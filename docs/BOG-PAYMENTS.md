# BOG გადახდები — ჩართვა და შემოწმება

კოდში მზად არის ბანკის hosted checkout: Visa/Mastercard, Apple Pay, BOG ნაწილ-ნაწილ
და განვადება. რეალური ან ბანკის Sandbox გადახდა ჯერ არ შესრულებულა: საჭიროა
მაღაზიის BOG ანგარიში და შესაბამისი API წვდომა. გასაღებების გარეშე checkout არ ქმნის
შეკვეთას, არ ცვლის მარაგს და არ აჩვენებს ყალბ წარმატებას.

## 1. ბანკისგან მისაღები წვდომა

ბიზნესბანკს/ბიზნეს მენეჯერს მიმართეთ ელექტრონული კომერციის გააქტიურებისთვის.
მოითხოვეთ Visa/Mastercard, hosted Apple Pay, BNPL („ნაწილ-ნაწილ“) და საჭიროებისამებრ
განვადება. თითოეული მეთოდი ბანკმა თქვენს merchant ანგარიშზე უნდა ჩართოს.
მოითხოვეთ ცალკე Sandbox `client_id`/`client_secret` და აქტუალური სატესტო ბარათების ინსტრუქცია.
Client Secret არ გამოაგზავნოთ ჩათში და არ ატვირთოთ GitHub-ზე; შეიყვანეთ Vercel-ის Environment Variables-ში.

Apple Pay მომხმარებელს ბანკის გვერდზე ეძლევა, შესაბამის მოწყობილობაზე/ბრაუზერში.
საკუთარ დომენზე პირდაპირი Apple Pay ღილაკი ამ ცვლილების ნაწილი არ არის.
BNPL/განვადების არჩევისას ბანკის გვერდი ასევე აჩვენებს ბარათს; ვადა, ლიმიტი,
პროცენტი და დამტკიცება ბანკის წესებით განისაზღვრება. კოდი მათ არ იგონებს.

## 2. ბაზის დამატება — ერთხელ, ჩართვამდე

საწყისი მდგომარეობაა `CHECKOUT_ENABLED=false`. ამ მდგომარეობით ახალი ვერსიის
merge/deploy არ საჭიროებს სქემის შეცვლას და ძველი ადმინი აგრძელებს მუშაობას.

შეინახეთ Neon backup/branch და პირველად ცალკე სატესტო branch-ზე გაუშვით
[`prisma/payments.sql`](../prisma/payments.sql), Neon-ის SQL Editor-ით ან `npm run db:payments`-ით.
SQL მხოლოდ `Payment` ცხრილს, მის ინდექსებსა და Order-ზე კავშირს ამატებს.
არსებულ პროდუქტებს, მომხმარებლებსა და შეკვეთებს არ ცვლის და არაფერს თესავს.
SQL ერთჯერადია; მეორედ შესრულებისას უკვე არსებული ცხრილი შეცდომას გამოიწვევს და ტრანზაქცია გაუქმდება.

არ გამოიყენოთ `db push`, `reset`, `seed` ან ძველი README-ის setup ბრძანებები რეალურ ბაზაზე.
ჩვეულებრივი `npm run build` მხოლოდ Prisma Client-ს აგენერირებს და სქემას არ ცვლის.
ამ პროექტს არსებული Prisma migration ისტორია არ აქვს; `db:deploy` ამ SQL-ის შემცვლელი არ არის.

## 3. ჯერ Sandbox — ცალკე Preview და ცალკე Neon branch

Sandbox-იც ამცირებს **იმ ბაზის** მარაგს, რომელთანაც აპია დაკავშირებული.
ამიტომ Preview-ს მიაბით ცალკე Neon test branch-ის `DATABASE_URL` — არასოდეს ცოცხალი მაღაზიის URL.
ბაზაში ყალბი პროდუქტების/შეკვეთების დასათესად სკრიპტი არ გაუშვათ.
`CHECKOUT_SANDBOX_ISOLATED=true` არის ამ დაყოფის ხელით დადასტურება;
კოდი Neon branch-ის იზოლაციას URL-დან ვერ ადგენს.
Sandbox დამატებით იბლოკება Vercel-ის `Production` deployment-ზე.

Vercel Preview-ის გარემოში შეავსეთ:

| ცვლადი | მნიშვნელობა/დანიშნულება |
| --- | --- |
| `CHECKOUT_ENABLED` | `true`, მხოლოდ SQL-ის შესრულებისა და ბანკის წვდომის შემდეგ |
| `APP_URL` | ამ Preview-ს სტაბილური საჯარო HTTPS origin, ბილიკის/პარამეტრების გარეშე |
| `BOG_ENVIRONMENT` | `sandbox` |
| `BOG_CLIENT_ID`, `BOG_CLIENT_SECRET` | ბანკის Sandbox მონაცემები, უსაფრთხო ველებში |
| `AUTH_SECRET` | არსებული ძლიერი საიდუმლო, მინიმუმ 32 სიმბოლო |
| `CHECKOUT_SANDBOX_ISOLATED` | `true`, მხოლოდ იზოლირებული ბაზის მიბმის შემდეგ |
| `BOG_APPLE_PAY_ENABLED` | `true` მხოლოდ ბანკის მიერ ამ მეთოდის გააქტიურების შემდეგ |
| `BOG_BNPL_ENABLED` | `true` მხოლოდ „ნაწილ-ნაწილ“-ის გააქტიურების შემდეგ |
| `BOG_LOAN_ENABLED` | `true` მხოლოდ განვადების გააქტიურების შემდეგ |
| `CRON_SECRET` | ცალკე შემთხვევითი საიდუმლო, მინიმუმ 32 სიმბოლო |

გადახდის callback არის `APP_URL/api/payments/bog/callback`.
Preview Deployment Protection არ უნდა ბლოკავდეს ბანკის callback-ს; ბანკს საჯარო HTTPS წვდომა სჭირდება.
`APP_URL` ყოველთვის ზუსტად იმ გარემოს უნდა ეკუთვნოდეს, რომლის ბაზასა და ბანკის წვდომასაც იყენებთ.
ცვლილების შემდეგ გაუშვით Redeploy.

კურიერის/ფოსტის ქალაქობრივი ტარიფები მომხმარებლის მოთხოვნით შემდეგ ეტაპზეა დატოვებული.
ამ ვერსიის სატესტო checkout ნაგულისხმევად იყენებს `CHECKOUT_DELIVERY=pickup`-ს;
`free` მხოლოდ მაშინ ჩართეთ, თუ მაღაზია ნამდვილად ფარავს მიწოდების ხარჯს.
რეალური გაყიდვების ჩართვამდე მიღებისა და საფასურის საბოლოო წესი უნდა განისაზღვროს.

## 4. სტატუსების პერიოდული გადამოწმება

ბანკის ხელმოწერილი callback, მომხმარებლის დაბრუნება და ადმინის „ბანკთან გადამოწმება“
წაიკითხავს ნამდვილ bank receipt-ს. დაკარგული callback-ისა და მიტოვებული გვერდის შემთხვევისთვის
დააყენეთ პერიოდული HTTPS მოთხოვნა, დაახლოებით ყოველ 5 წუთში:

```text
GET APP_URL/api/checkout/reconcile
Authorization: Bearer <CRON_SECRET>
```

გამოიყენეთ თქვენი გეგმით მხარდაჭერილი scheduler. `vercel.json`-ში ფასიანი/ხშირი cron
ავტომატურად არ დამატებულა, რომ არსებული უფასო deploy არ დაბლოკილიყო.
Endpoint მაქსიმუმ 10 მცდელობას ამოწმებს ერთ გაშვებაზე; მუდმივი დატვირთვისას აკონტროლეთ
გაუნაღდებელი შეკვეთების backlog და გაზარდეთ სიხშირე/გამტარუნარიანობა.

მხოლოდ ჩვენი 15 წუთის გასვლა ნაშთს არ აბრუნებს — ჯერ ბანკმა უნდა დაადასტუროს
წარუმატებლობა ან ვადის ამოწურვა. კავშირის გაურკვეველი შედეგი გადადის გადამოწმებაში;
ნაშთი რჩება დაჯავშნილი. ეს იცავს იმ შემთხვევას, როცა თანხა ბანკმა მიიღო, პასუხი კი დაიკარგა.
დუბლირებული callback მარაგს მეორედ არ ცვლის. დაბრუნებული ჯავშნის შემდეგ დაგვიანებული
წარმატება ითხოვს ხელით განხილვას/ბანკში დაბრუნებას და შეკვეთას ავტომატურად არ ასრულებს.

## 5. საბანკო ტესტის გასავლელი სცენარები

იზოლირებულ Preview-ზე ბანკის მიერ მოწოდებული სატესტო ინსტრუქციით შეამოწმეთ:

1. წარმატებული ბარათი: სწორი თანხა, შეკვეთა ადმინში, ნაშთის ერთი ჯავშანი, დადასტურებული გადახდა.
2. უარყოფილი/ვადაგასული გადახდა: ჯავშნის ზუსტად ერთხელ დაბრუნება ბანკის დადასტურების შემდეგ.
3. მომხმარებლის დახურული გვერდი: callback/scheduler დამოუკიდებლად ასრულებს გადამოწმებას.
4. უკან დაბრუნება/refresh/ღილაკზე ორჯერ დაჭერა: მეორე შეკვეთა ან დამატებითი ჩამოჭრა არ ჩნდება.
5. ერთ ბოლო ნივთზე ორი კალათა: მხოლოდ ერთი ჯავშანი სრულდება.
6. Apple Pay თავსებად მოწყობილობაზე; BNPL/განვადების პირობები და ბანკის უარყოფა.

Sandbox შეკვეთები მონიშნულია TEST-ით, რეალურ მიწოდებაში ვერ გადადის და გაყიდვების ანალიტიკაში არ ითვლება.
ბარათის ნომერი/CVV ამ საიტის ფორმაში არ იწერება და ბაზაში არ ინახება.

## 6. რეალურ რეჟიმზე გადასვლა

საბანკო ტესტების გავლის შემდეგ იგივე SQL ცოცხალ ბაზას ერთხელ ემატება.
Vercel Production იყენებს მხოლოდ Production BOG წვდომას, `BOG_ENVIRONMENT=production`-ს,
საიტის სწორ `APP_URL`-ს და ბანკის მიერ ნამდვილად ჩართულ მეთოდებს.
ამის შემდეგ ირთვება `CHECKOUT_ENABLED=true` და სრულდება Redeploy.
ეს ცვლილება Production გადახდას ავტომატურად არ რთავს.

ადმინი ცალ-ცალკე აჩვენებს გადახდასა და მიწოდებას. გაუნაღდებელი ან TEST შეკვეთის
გაგზავნა დაბლოკილია. ონლაინ შეკვეთის პირდაპირი გაუქმება/ნაშთის დაბრუნება დაბლოკილია:
ჯერ საჭიროა ბანკში სწორი გაუქმება/თანხის დაბრუნება და ფიზიკური მარაგის შეფასება.
სრული/ნაწილობრივი refund API ამ ეტაპზე არ დამატებულა; შესაბამისი receipt გადადის REVIEW-ში,
მარაგი ავტომატურად არ ბრუნდება. მომხმარებლის მისამართისა და კონტაქტის რედაქტირება შენარჩუნებულია.

## ტექნიკური შემოწმებები

```sh
npm run test:bog
TEST_DATABASE_URL=<მხოლოდ-local-topuria_v7_test> npm run test:checkout
npm run typecheck
npm run build
```

`test:checkout` ტესტავს ნამდვილ იზოლირებულ PostgreSQL ტრანზაქციებს, ბანკის პასუხები კი mock-ია.
ბანკის კონტრაქტის ტესტებიც mock მოთხოვნებს იყენებს. მათ არ ჩამოუჭრიათ რეალური თანხა.
`tests/checkout-browser.py` ამოწმებს ინტერფეისს; გადახდის პასუხები მხოლოდ ბრაუზერის ტესტში იცვლება.
საჯარო API-ს არ აქვს fake-payment/mock-success რეჟიმი.
